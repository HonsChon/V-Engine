## 背景与目标

v1.2 的水面反射基于 SSR（屏幕空间步进）。四轮算法迭代后（详见
SSR_Water_Rendering.md 调试记录），确认其固有局限无法用调参消除：

| SSR 固有局限 | 后果 |
|---|---|
| 无法反射被遮挡/屏幕外几何 | 球体背后区域的倒影点状蓝色回退 |
| 轮廓歧义（守卫两难） | 倒影拉长成条纹 vs 缺失，不可兼得 |
| 逐像素 jitter | 点状噪声（需 TAA 掩盖，本引擎暂无） |

路线图早已规划替代方案：**平面反射（Planar Reflection）**——镜像相机 +
半分辨率反射 RT，平坦水面精确反射，业界标准做法（UE/Source 同款）。

## 方案设计

### 核心算法（四要素）

```
主相机 eye                          镜像相机 eye' = eye 关于水面翻转
    \                                    /
     \  看向水面点 P                     /  同一屏幕位置 s 的光线
      \                                /
   ────●──────────────────────────●────  ← 水面 y = h（镜像平面）
```

1. **镜像相机**：`V' = view · M`，`M = T(0,2h,0)·S(1,-1,1)`。注意镜像的是
   整套相机位姿（含 up 向量翻转，镜像相机"倒立"于水下），不是只挪位置。
2. **恒等屏幕 UV**：镜像相机与主相机共用同一投影矩阵 → 水面上的点
   （`M·P = P`，平面不动点）在两幅图像中投影位置相同 → 水面片元直接
   `texture(reflectionRT, gl_FragCoord.xy / screenSize)`，零投影计算。
3. **斜近裁剪投影**：把投影矩阵的近裁剪面替换为水面平面，硬件逐三角形
   剔除水下几何（纯 CPU 矩阵技巧，零着色器改动）。
4. **绕序修正**：镜像矩阵 det=−1 翻转屏幕绕序，需调整 frontFace 保持外表面。

### 关键工程决策

| 决策 | 理由 |
|---|---|
| **复用 pbr_vert/frag.spv**（零新场景着色器） | pbr 着色器对相机的全部认知来自 UBO 的 view/proj/viewPos，无屏幕空间假设 → 换上镜像矩阵即可，自动得到与主画面一致的光照 |
| **借用 ForwardPass 材质布局** | ReflectionPass 的 Set1 用 `m_forwardPass->getMaterialLayout()`，RenderSystem 每帧已分配的材质描述符直接兼容，零额外分配 |
| **半分辨率 RT** | 业界标准省法：≈1/4 像素成本，Linear 采样平滑 |
| **SSR 保留可切换** | DebugPanel「Water Reflection」开关 + 扰动滑条，便于 A/B 对比 |
| **结构抄现有范式** | RT/RP/FB 抄 SSRPass；绘制循环抄 TransparentPass；纹理输入抄 LightingPass::setGBufferInputs——不发明新模式 |

### 管线位置

```
GBuffer → Blit SceneColor → SSAO → SSR(遗留) → 【ReflectionPass】
→ 合成 [Lighting → Transparent → Water(SrcAlpha 混合)]
→ 离屏目标 → FXAA → UI → Swapchain
```

## 调试历程

> 五轮迭代，三轮误诊。每轮记录：现象 → 假设 → 验证 → 结论。

### 第一轮：地面 Plane 挡住了水面

**现象**：倒影只显示"碗状碎片"，球正下方大片水面空白。

**用户定位**（关键一环）：默认场景的地面 Plane（y=−1.5）与水面完全共面——
它是不透明几何，深度写入 GBuffer，water.frag 的深度遮挡逻辑在共面处把
水面 alpha 压到近 0 → 反射被它盖住。

**修复**：移除共面 Plane 实体（水面自身承担地面职责）。

**教训**：场景配置可以伪装成渲染 bug；用户对场景的了解是第一手诊断信息。

### 第二轮：RenderDoc 发现"半个球" → 误诊为绕序

**现象**：RenderDoc 抓反射 RT，球只画了**远水那一半**（贴水半球缺失）。

**假设（错误）**：`frontFace=Clockwise` 把近侧外表面剔除了，渲染出远侧
内表面 → 改成 CounterClockwise。

**验证**：用户反馈"至少下半部分对了"——部分改善（实际是巧合，见第四轮）。

**后续**：又观察到"倒影像球内部" → 改回 Clockwise → 现象反复，
`Clockwise`/`CounterClockwise` 两次翻转都"有时对有时错"。

**真相**（第三轮揭晓）：绕序从来没坏——"半个球"的根因是深度约定错配
（下述）。pbr.frag 的 `if (!gl_FrontFacing) N = -N` 会给错误侧面翻法线，
使内表面渲染"看起来合理"，大幅强化了误诊。

**教训**：
- **一个症状一个根因的假设要穷尽**：本轮把"内容少一半"和"内容是错侧面"
  混为一谈，实际上前者是裁剪问题、后者当时并不存在。
- 调参后"看起来好转"≠ 假设正确（回归均值/视角变化都会伪装成改善）。

### 第三轮：深度约定错配（真正的根因之一）

**数值复算**（手工推导 + 与 RenderDoc 对照）发现引擎级隐患：

```
引擎：GLM 默认 GL 约定深度 z_ndc ∈ [−1, +1]（未定义 GLM_FORCE_DEPTH_ZERO_TO_ONE）
API：  Vulkan/DX12 都按 [0, +1] 裁剪

普通渲染：z_ndc<0 只发生在距相机 <0.2 单位处 → 从未被察觉
斜近裁剪：Lengyel 原式把水面映射到 z_ndc = −1（GL 近平面）
        → 贴水上方整段带 (z_ndc∈[−1,0)) 落进 API 裁剪区被硬裁
        → RenderDoc 里"只剩远水一半"
```

DX12 数值验证完全吻合（球底 z_ndc=−0.708 被裁 / 球顶 +0.508 可见）。

**修复**：重写 `makeObliqueProjection` 为 **[0,1] 约定版**——第三行
`r = k·C`（水面映射到 z_clip=0），`k = 1/dot(C,Q)`，远角 Q 的符号自适应
（Vulkan 投影 Y 翻转会使 D 变号，取对侧角即兼容双后端）。

**教训**：
- **多层约定叠加（网格绕序 × GLM × API Y 翻转 × 镜像 det）中，纯推导极
  易差一个符号——每一步都要有数值验证或 RenderDoc 实测兜底**。
- 深度约定这类"平时无害"的引擎级错配，会在特殊技巧（斜裁剪/阴影矩阵）中
  被放大成可见缺陷。

### 第四轮："空 RT"迷局与截图工具陷阱

**现象**：用 PrintWindow 自动截图对比 `Clockwise`/`CounterClockwise` 两版
构建，最终画面逐像素 diff = 0——按"绕序翻转必然改变渲染面"推理，这不
可能。陷入"pass 没执行？绑定坏了？剔除没生效？"的多轮排查（品红清屏
探针证明 pass 执行 + 绑定正常；cull=None 探针排除剔除；关深度探针排除
深度；`drawn=2` 日志排除零绘制）。

**转机**：用户 RenderDoc 抓帧显示 **RT 内容正确**——与我方截图"空 RT"
直接矛盾 → PrintWindow 抓到的是**陈旧帧**（DWM 缓存/时序问题），此前基于
它的多个"零差异"结论全部作废。

**另一个工具陷阱**：`--cam` 指定的相机位姿被 autotest 按键 `5` 触发的
展示位姿重置覆盖 → 九个俯角的扫描截图全部是同一机位（std 完全相同暴露）。

**修复**：
- 展示位姿仅在无 `--cam` 覆盖时生效；
- 截图结论降级为"参考"，**以 RenderDoc 抓帧为准**。

**教训**：
- **验证工具本身也需要验证**——用"两次运行应不同的已知差异"自检工具链。
- 自动化截图与 GPU 实况之间可能隔着一层缓存；对"不可能的零差异"要先怀疑
  测量，再怀疑代码。

### 第五轮：转动相机时倒影突然消失/复现

**现象**：转动视角时倒影突然消失，动一下又回来。

**数值定位**：斜裁剪的远平面绕「水面∩远平面」交线倾斜，倾斜度
`k = 1/D`，`D ≈ sin(可见侧远角仰角) − 相机高出水面/far`。旧参数
（far=100）下，俯角 0°~−8° 附近约束值（0.26~0.34）恰好扫过球顶倒影的
内容比（0.36）→ 转动时倒影顶部闪进闪出。

**两段修复**：
1. 反射专用基础投影 far 100→1000：崩溃带 ∝ h/far，先缩小一个量级；
2. **k 钳制上限 1.5**（治本）：`r = k·C` 对任意 k>0 都把水面精确映射到
   z=0（水下剔除不受影响），k 只决定远平面倾斜度。水面入画时反射内容的
   `C·p/w` 理论极限 ≈ tan45° = 1，kmax=1.5（约束 0.67）全覆盖，且 RT
   深度无后续消费，安全。

**验证**：俯角扫描（−60°~+20°，std 度量反射结构）+ 用户转动实测 →
倒影平滑跟随视角，无突变。

**教训**：带"钉扎/翻转"的数学构造里，参数过阈值时行为会**突变**——
排查"间歇性"症状时要找离散阈值（sgn 翻转、k→∞、布尔开关），
而不是连续量。

## 最终架构

```cpp
// SceneRenderer::updateUniforms（每帧）
glm::mat4 mirror = T(0, 2h, 0) · S(1, -1, 1);
glm::mat4 reflView = view * mirror;
glm::vec4 clipPlane = (reflView⁻¹)ᵀ · (0, 1, 0, -(h + 0.02));   // +0.02 防共面闪烁
glm::mat4 reflProjBase = YFlip(perspective(fov, aspect, 0.1, 1000));  // 反射专用 far
reflUBO.proj = makeObliqueProjection(reflProjBase, clipPlane);
```

```glsl
// water.frag（双模式）
if (ubo.reflectionParams.x > 0.5) {
    vec2 distortion = perturbedNormal.xz * ubo.reflectionParams.y * 0.5;
    reflectionColor = texture(reflectionRT, clamp(screenCoord + distortion, ...)).rgb;
    reflectionStrength = 1.0;              // 精确命中，无衰减
} else { /* SSR 步进（回退/对比） */ }
```

**配置速查**：

| 参数 | 值 | 说明 |
|---|---|---|
| RT | RGBA8 + D32，半分辨率 | 与主画面同格式（pbr.frag 已输出 tonemap LDR） |
| frontFace / cull | **Clockwise** / Back | 镜像绕序补偿，保留外表面（贴水侧） |
| 深度测试 | (true, true, Less) | 正常深度 |
| 斜裁剪 k | min(1/D, 1.5) | 水面→z=0 精确；防远平面倾斜吃内容 |
| 反射 far | 1000（主画面 100 不变） | 缩小倾斜咬合区 |
| 裁剪面偏置 | h + 0.02 | 防共面几何逐像素闪烁 |
| 相机水下 | 仅清屏（天空色回退） | 镜像相机失效域 |

## 经验教训汇总

1. **实测优先于推导**：绕序符号穿过多层约定（网格×GLM×API×镜像），
   纸面推导两次都差一个符号。RenderDoc 抓帧 + 数值复算才是终审。
2. **一个症状可能有多层根因**：本轮叠了三层——共面遮挡（场景）、深度
   约定错配（引擎级）、k 失稳（算法级）——逐层剥开，每层都曾伪装成
   "唯一根因"。
3. **验证工具需要自检**：PrintWindow 陈旧帧 + `--cam` 被展示位姿覆盖，
   两个工具陷阱各自制造了一轮"鬼排查"。
4. **"改了就好"不等于"改对了"**：第二轮绕序翻转后的"好转"是巧合；
   验收要找与假设直接对应的判据（如 UFO 圆顶朝向、RT 半球内容）。
5. **间歇性症状找离散阈值**：sgn 翻转、k→∞、布尔开关——连续调参解释不了
   的"突然消失/复现"，背后几乎必有离散切换。
6. **用户的场景知识和肉眼是最高带宽的调试器**：共面 Plane、"像球内部"、
   "转动时消失"三条关键线索全部来自用户观察，且各自指向一个真实根因。
